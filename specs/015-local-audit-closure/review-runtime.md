## Resolved P1 — An ordinary failed runtime kill was promoted into confirmed cancellation

`src/cli_agent_orchestrator/services/terminal_service.py:5488` ignores the boolean result from `get_backend().kill_window(...)`; its exception handler also leaves `runtime_complete` true. This differs from the exact terminal cleanup path, which correctly requires a reclaimed outcome. If FIFO/provider cleanup succeeds, `dismantle_terminal_runtime` returns true even though the ordinary writer could remain alive. `delete_terminal` then removes the registry row. `local_peer_service.py:1423` trusts that result and persists `worker_stopped=true`, followed by project lease release at line 1442.

Reproduction: ordinary non-KAS/non-tombstone metadata; make the backend kill return false, or raise a runtime exception, while other cleanup succeeds. Cancellation can return a durable canceled receipt and make the shared project available while the old worker still writes. This violates C-001 and US1 acceptance 1. It is task-relevant even though the incorrect stop boundary predates this feature: the new receipt explicitly claims that boundary provides stop proof.

A memory-light executable check compiled the exact AST function from the current source with dependency stubs (no edited function body). Both `kill_window=False` and `kill_window raising RuntimeError('still alive')` produced `runtime dismantled=True`. Existing peer cancellation tests stub `delete_terminal=True`, so they cannot detect this composed failure. Require positive ordinary runtime stop acknowledgement, retain retry metadata/resources and the project fence on an unproven result, and test cancellation through that real service boundary.

## Resolved P2 — Cursor eviction between attach validation and replay hid a history gap

`src/cli_agent_orchestrator/api/main.py:2624` checks that `/events`' cursor is retained before returning `StreamingResponse`. Its generator registers the live subscriber later, then calls `after_id` at line 2642. `event_log_service.py:150` deliberately returns all retained rows when the cursor is no longer found. If the ring advances between these operations, an originally valid cursor can be evicted along with newer undelivered rows. The consumer receives the retained suffix/live stream without `event_cursor_expired` or an explicit resync signal. The MCP descriptor precheck does not close this attach race. AG-UI has the same separate validation/replay pattern.

Reproduction using the actual EventLog module: append cursor A, verify A is retained, append 501 subsequent records, call `after_id(A)`. It returned 500 rows starting at post-cursor sequence 1, silently omitting sequence 0. This is possible at the endpoint boundary before the first generator advance; the live queue is not yet registered. An eviction can also occur during awaited authorization before replay. The contract expressly requires expired cursors to resync rather than hide gaps.

Require a retained-cursor validation and replay snapshot taken together after live registration, with a visible expired-cursor outcome if validation fails. Preserve AG-UI derived frame cursor behavior and existing workflow cursor contracts. Add a focused attach interleaving case; ordinary history-to-live tests alone do not exercise this condition.
