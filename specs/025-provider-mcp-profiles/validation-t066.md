## Source diagnosis

- `specs/001-verifiable-orchestration/workflow-status.md` T052 (lines 1849–1867) defines retry as exact stop/release and planned-generation creation only. It explicitly does not enqueue, claim, send, or resume.
- `src/cli_agent_orchestrator/services/work_service.py` (494–576) checks the reconcile generation, releases its scheduler reservation, then calls `WorkRepository.retry_work`; it does not bind a fresh order or queue the replacement.
- `src/cli_agent_orchestrator/clients/work_repository.py` (3028–3097) creates the next attempt in `planned` under revision fencing.
- `src/cli_agent_orchestrator/services/work_admission.py` replay paths (365–393, 447–523) validate the original attempt and original durable binding. Initial launch admission binds and queues generation one (813–859). The original idempotency replay therefore remains read-only and cannot admit a later generation.
- `src/cli_agent_orchestrator/clients/work_postgres_schema.py` has a unique `(principal_id, selector, idempotency_key)` on immutable initial launch-origin rows. `src/cli_agent_orchestrator/services/work_contract.py` validates that row against the immutable work-item request identity. Copying the original row or changing the original key is not a valid replacement protocol.
- Before T066, Work schema was V3 (`work_repository.py:459`, migrations in `work_postgres_schema.py:707–711`). T064/FR048's no-schema constraint remains local to that dispatcher feature; T066 introduces a separate additive V4 schema contract.

## Implementation boundary

T066 adds `LaunchRuntime.resolve_replacement` / `admit_replacement` for a caller that already completed trusted `WorkService.retry_work`. It requires an explicit selector and a runtime-sealed generation/work/revision/action identity, revalidates the verified principal and active provision under the provision-selector lock, and composes `WorkContracts`, `WorkDeliveries` and `WorkScheduler` in a caller-owned transaction. New `WorkRetryOrigins` records the original launch root, exact reconciled predecessor, released reservation and matching release/replan actors/events, current authority/provision/contract/snapshot/delivery, and exact new scheduler request. V4 is additive and immutable; the initial launch-origin row and `retry_work` planned-only behavior remain unchanged. Admission neither stops work nor claims, sends, or issues credentials. The existing scheduler keeps capacity, fairness, dependency, reservation, budget and dispatch ownership. No public endpoint, automatic retry path, caller-supplied stop proof, legacy bypass, schema backfill or prior-generation credential/delivery reuse is in scope.
