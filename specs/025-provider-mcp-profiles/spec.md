# Provider MCP profiles and current acceptance

Date: 2026-10-20. Status: incremental implementation in main; no live acceptance inferred.

## User scenarios

1. **P1: Diagnose current failures.** An operator can distinguish a provider timeout from an authentication dialog, monitor failure, tool denial, or missing receipt using sanitized evidence. A historical record remains unresolved until causal evidence exists.
2. **P1: Restrict agent collaboration.** An operator selects an explicit interaction or collaboration profile. The agent sees and can invoke only the selected operations; direct calls to other operations are rejected before dispatch. Human answers still require their existing authority.
3. **P2: Extend authority deliberately.** Coordinators, knowledge writers and elastic workers receive separately reviewed tool sets; the basic collaboration profile never implicitly gains those operations.
4. **P2: Accept current binaries and source.** Each provider/version is validated with isolated configuration, persistent messages/interactions, AG-UI projection, restart and owned cleanup. Offline results and historical receipts remain distinct from final acceptance.

## Requirements

- FR-001: Retain the exact restricted three-tool interaction profile and existing unmarked behavior for compatibility.
- FR-002: The initial collaboration profile adds only `send_message`, `list_siblings`, `cao_list_interactions`, `cao_get_interaction`, and `cao_escalate_interaction`. It excludes answering human questions, delegation, supervision and memory writes.
- FR-003: A selected profile must filter both catalog and direct dispatch, including unknown names and collisions. Resources, resource templates and prompts must remain inaccessible in restricted profiles.
- FR-004: Profiles restrict surface; they do not grant operation authority, broaden provider-native permissions or replace existing interaction, identity, project and server-selector checks.
- FR-005: Unknown or malformed explicit profile values fail closed before provider launch or server execution. Selection is per MCP child. Configuration supplied for another server must not receive CAO's protected policy or capability.
- FR-006: The historical OpenCode child marker always preserves the exact three-tool restriction, even when combined with a broader profile. Existing profiles are never silently widened.
- FR-007: Evidence must cover permitted/denied calls, empty/partial client permissions, cross-instance isolation and the entire registered CAO tool catalog. Final live acceptance must bind the source and runner actually executed.
- FR-008: Current Claude failures are diagnosed without changing the operator login or extending the 180-second task deadline. Intensive live tests are serialized after a fresh memory check. Reuse PostgreSQL only after identity verification.
- FR-009: Work messaging (`cao.work.message`) and generic `send_message` have separate acceptance. Preserve historical `RECONCILE_REQUIRED` records. OpenCode v1 requires its own pinned real binary. QEMU is limited to the four remaining cases.

## Success criteria

- SC-001: In offline transport tests, both profile catalogs and direct invocation match their exact sets, and every excluded registered operation is denied before its handler executes.
- SC-002: Independent child instances cannot affect each other's policy. Malformed selections do not reach unrestricted startup.
- SC-003: Existing interaction contracts and affected configuration tests continue passing without changed gates.
- SC-004: Each numbered provider pending item has an explicit execution task or deferred acceptance task below; completed means evidence exists, not merely a proposal.

## Assumptions and scope

The first implementation adds an opt-in server policy primitive through CAO's existing protected MCP configuration overlay. It does not yet enable expanded provider permissions, change OpenCode's legacy three-tool marker, implement coordination profiles, or claim a real provider acceptance. Those are dependent tasks. The user authorized ongoing implementation and subsequently requested commits and push of all accepted work to main. Known failing global gates remain distinct from that publication instruction.

## Timeout observability increment (CL-01, 2026-10-20)

- FR-010: A completion timeout must expose only factual, closed observations: completion phase, final terminal status, whether working was observed, receipt-probe error count, whether a receipt candidate was seen, current stable receipt observation count and whether idle extraction was attempted. It must retain kind/status, delivery uncertainty, existing deadlines, quota/error precedence and no-retry semantics.
- SC-005: Offline timeout tests must distinguish no-pickup, observed work, candidate receipt and probe error without retaining Unicode prompt/receipt/error content. An API-boundary test must propagate those observations without changing the existing 504 or non-timeout responses. These observations are diagnostic, not a demonstrated historical cause or a new completion signal.

## T007 increment: effective client filters and profile-aware preflight

- FR-011: OpenCode v2 preflight must require every tool in the effective selected profile, reading the generated child's actual `environment` field. The historical marker intersects that profile with the three interaction tools; absent profile metadata retains the existing three-tool preflight. Invalid profile/environment shape or a policy in an ignored environment field must fail before launch. Existing last-rule-wins/resource/name-collision and Code Mode checks remain unchanged.
- FR-012: With an explicit profile, Codex's advertised `enabled_tools` must be the intersection of the selected server policy and any explicit client allowlist. An absent/None client filter becomes the profile's set; an empty filter stays empty; partial filters are never expanded. Unknown/banned names are removed, malformed lists fail before launch, and the legacy marker can only narrow the policy. Profiles without an explicit policy retain existing behavior. No operation authority or native file/shell permissions are granted by this transformation.
- SC-006: Offline tests must demonstrate v2 rejection when any collaboration tool lacks its effective client grant, exact legacy-marker intersection, invalid selections/environment rejection, and Codex's emitted TOML for empty/partial/absent filters and special quoted tool names without broadening.

- FR-013: Explicit `cao_tool_profile` may be consumed by OpenCode installation only through the managed per-agent publication protocol of FR-018–022. Invalid selections/declarations fail before native/provider/context writes. Direct shared native config translation continues rejecting unconsumed metadata instead of silently discarding it. Existing unmarked profiles retain legacy installation support. The earlier T021 interim guard remains historical evidence, superseded for valid managed installs by T022.

- FR-014: A rejected installation must exit the CLI with a nonzero status while retaining the existing sanitized `Error:` message. A service result with success=false must not be reported to shell callers as successful exit 0. Successful installations remain exit 0.

- FR-015: OpenCode installation must also reject either reserved policy marker supplied in env/environment, before a per-agent selection can leak into a shared MCP declaration. This guard does not claim atomic rollback of existing URL download or --env staging behavior; it guarantees the native/provider-record/context boundary after profile resolution.

## Reproduced native catalog startup race

- FR-016: The isolated OpenCode v2 catalog test must not treat a ready /doc endpoint as proof that its private service.json authentication receipt is already readable and complete. It must wait for a nonempty string password only within the existing shared 15-second startup deadline, stop when the owned service exits, and retain the existing HTTP/catalog assertions, process cleanup and 45-second outer bound. No operator credential path or login is used.
- SC-007: Offline regression tests cover delayed receipt creation, partial JSON, invalid/missing password, deadline expiry and exited service. A single corrected native catalog execution must bind the existing pinned binary; preserve the prior failed receipt instead of overwriting it.

## T007: explicit-policy preflight without interaction opt-in

- FR-017: OpenCode v2 initialization must validate the effective generated grants for every enabled canonical CAO MCP child carrying an explicit tool profile, even when the terminal has not requested the interaction channel. Multiple configured children must each pass. The existing interaction request still validates its selected child. Unprofiled launches without interaction opt-in preserve their legacy behavior; successful profile validation alone never advertises an interaction capability.
- SC-008: Initialization regressions must reject absent/partial grants and a denied second profiled server before backend launch, clean owned temporary configuration on failure, and accept complete grants in both native MCP layouts without mutating the source config or enabling an unrequested interaction channel. Disabled children remain inactive. This does not enable native policy installation or close T022.

## T022: native per-agent publication protocol

- FR-018: CAO-managed OpenCode tool profiles must reside in one versioned, bounded, strictly parsed envelope in the native agent body, not in extra native-schema fields, the shared MCP environment, or the best-effort grant record. Installation reserves the envelope prefix. Before provider/context/MCP writes, an atomic agent replacement publishes `pending`; the final atomic replacement publishes `ready` with a binding to the selected native metadata/body, selected-agent tool overrides and profiled shared server declarations. Failures before final replacement leave pending or the previous complete artifact. An ordinary legacy install without an envelope retains its existing artifact behavior.
- FR-019: Reinstalling an already managed agent without a selected profile keeps the envelope with an empty profile map; a failed replacement must not silently remove its guard. Unknown/malformed/pending envelopes, mismatched identity/content/configuration, absent/disabled bound servers and reserved prompt prefixes fail before managed launch. Explicit source commands must be canonical when installing. Shared MCP serialization retains its existing persisted-command resolution; only a validated profiled child is pinned to the current CAO module in the private runtime copy.
- FR-020: CAO v2 launch must use one frozen selected-agent payload and the shared configuration snapshot against which its policy binding was checked. It strips the envelope from the model system prompt, omits other managed agents from the private catalog, applies the selected profiles before the protected overlay, and retains T027's live grant preflight. Other unmarked agents retain existing behavior. CAO v1 rejects managed envelopes, including empty-profile envelopes.
- FR-021: The envelope provides installation consistency, not authenticity against an operator deliberately editing/removing its content. Policy enforcement is supported only through CAO-managed v2 launch. Direct external OpenCode invocation against shared files is not an accepted profiled launch. Shared global tool entries are not part of the binding because unrelated installs update them; effective grants are validated against the actual generated config at launch. A failed plugin refresh can leave a managed agent pending and require explicit reinstall.
- SC-009: Integration tests must prove valid profile installation and private launch, two agents with distinct policy over a common server, unchanged shared policy/legacy persisted commands, invalid-source preservation, failures before pending and during provider/context/native/MCP/final writes, repair/reinstall and managed-to-legacy transition, stale/tampered/pending bindings, v1 refusal, frozen-input TOCTOU behavior and private-catalog/prompt isolation. Existing reserved environment/direct-translation guards and legacy installation tests remain required. These offline contracts do not establish live provider acceptance.

- FR-022: Before marking a managed installation ready, compare each selected shared server declaration with the exact translation prepared from its validated canonical source; a mismatch leaves pending. Explicit profiled sources with disabled/non-boolean flags or non-local transports must fail before publication. The binding hashes native metadata/content as canonical JSON, avoiding dependence on YAML formatting.

## T006 observation continuation

- FR-023: Completion timeouts must distinguish attempted receipt probes from empty results and attempted prompt recovery from verified delivery. Add factual `receipt_probe_calls`, `prompt_redelivery_attempts` and `delivery_verified` fields without changing recovery, receipt settling, deadline, auth or error precedence. Recovery attempts include failed or suppressed sends and are not proof of duplicate delivery. The matrix sanitizer must accept the complete old or complete extended diagnostic shape, reject partial/unknown or wrongly typed fields, and preserve no prompt/receipt text. The existing stable count remains the current streak, not a historical maximum.
- SC-010: Prove empty/raising probes, recovery success/failure and API/sanitizer propagation offline before a serial source-bound Claude diagnostic. A diagnostic run is separate from full matrix acceptance; leave T006 open unless executable evidence actually localizes its failure boundary.

## T007 Claude explicit filter continuation

- FR-024: For a CAO-managed Claude MCP entry with an explicit CAO tool profile, consume a non-null `enabled_tools` list as an additional exact-name restriction. Empty means no tools; partial/unknown entries may only reduce the selected profile. Remove this client metadata from Claude's generated server entry and encode the bounded intersection in a protected child environment variable. Null/absent filters retain the selected profile. Malformed non-null filters fail before returning a launch command; legacy unprofiled entries retain their existing serialization.
- FR-025: Server startup must strictly validate a supplied internal filter, require an explicit profile, and snapshot its immutable intersection before serving requests. Malformed, oversized, unknown or out-of-profile internal names abort startup. Catalog and direct calls use the same restricted set; resources/prompts stay denied. Profile-controlled environment cannot forge this variable on any server; native OpenCode shared installation must reject it. Existing native grants, operation authority, capability protection and the historical three-tool middleware remain additional independent restrictions.
- SC-011: Reproduce the Claude serialization/dispatch gap using its real builder and actual MCP transport, then verify empty/partial/unknown filters, malformed filters, unfiltered legacy behavior, cross-instance isolation, ignored/forged environment and startup rejection. This does not accept a live Claude model, native-wrapper profiles or OpenCode native `enabled_tools` propagation, and does not close T007 as a whole.

## T007 native routing policy refusal

- FR-026: A Claude profile routed through a nonempty `native_agent` must reject any explicit `cao_tool_profile` declaration in its resolved MCP entries instead of silently discarding it. Presence is decisive even for null/invalid values, aliases or untrusted commands. Check mappings and the supported Pydantic server-model representation. Refuse before returning a command, emitting MCP/prompt artifacts or sending backend input, using a fixed message without user-supplied names/values. Native wrappers without explicit CAO policy and the full CAO decomposition path retain their routing and permissions.
- SC-012: Prove refusal through direct command building and initialize-with-fake-backend, including known/invalid/null policy values, mapping/model entries, permissive native grants and preloaded profiles. Retain legacy native routing, missing-profile fallback, model override and full-CAO filtered configuration tests. Run a new, separately scoped unit selection, typing/style and composition; do not reactivate T032's deferred 16-module/two-stdio validation or claim vendor/native policy acceptance.

## T007 native installation filter refusal

- FR-027: Until native per-agent envelopes support explicit client filters, OpenCode installation must reject a non-null `enabled_tools` on an explicitly profiled MCP declaration before pending/native, provider, context or shared-config publication. Empty, partial, unknown and malformed values must never silently become the full selected profile. Null/absent and legacy unprofiled declarations retain their behavior. Use a fixed error without echoing supplied server names or values; explicit import/download/--env staging retains its documented earlier effects.
- SC-013: Reproduce the dropped-filter boundary through native preparation and real install/CLI control flow. Verify fresh-install refusal and preservation of an already managed installation, source and context/config artifacts. Prove null/absent profiled installation and legacy preparation compatibility. Keep actual filter propagation, T007 and live/global acceptance open; do not resume deferred T032 validation.

## OpenCode native explicit filters

- FR-028: Extend native policy envelopes with a strictly parsed version two carrying immutable per-server exact-name filters, bound with the native payload and selected configuration. Keep unfiltered version-one bytes/bindings compatible. Empty filters deny all, partial/unknown client names only narrow, malformed filters fail before publication. Never put per-agent filters in shared MCP config. Retain pending/ready, failure recovery, v1 refusal and frozen private launch.
- FR-029: Propagate a managed filter through private OpenCode array-command overlay to the existing protected MCP filter variable, consuming client metadata before translation. Preflight validates the same profile/filter/legacy intersection, rejects forged/ignored/malformed internal filters, and requires all three tools when the interaction channel is explicitly requested. Restricted server catalog and direct calls remain identical.
- SC-014: Prove version-one compatibility, strict version-two schema/binding/nonmutation/isolation, install and repair with empty/partial filters, actual provider initialization in both layouts, effective grants and opt-in refusal, and in-process MCP catalog/call dispatch. No live acceptance or deferred T032 validation is implied.
