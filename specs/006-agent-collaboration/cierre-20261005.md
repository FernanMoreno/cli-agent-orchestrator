## Qué ya existía y se reutilizó

Las 23 casillas abiertas no representaban 23 funcionalidades ausentes.
`assign`, `handoff`, caller, inbox, recibos, reconciliación y worktrees ya tienen
propietarios y suites. Spec008 conserva aceptación nativa de coordinación y
reinicio del 2026-10-02; spec007 conserva aceptación de implementación real y
dos rondas con los tres proveedores del 2026-10-05. Son evidencia histórica
con sus límites; no prueban por sí solos las nuevas fronteras de esta tanda.

Se reutilizan `test/fixtures/cao_server.py`, SQLite, HTTP, tmux y las suites
existentes. `scripts/agent_collaboration_acceptance.py` añade escenarios al
runner existente, sin crear otro coordinador ni otra base de datos.

## Errores reproducidos y correcciones

### 1. El CLI normal no enviaba autenticación

`cao launch` adjuntaba bearer en la ruta Work, pero la petición normal a
`/sessions` no lo enviaba. La nueva regresión falló antes del cambio.
Ahora usa `get_local_bearer()` y una cabecera `Authorization`. El token no
entra en query params ni en la salida del CLI. La ruta Work se conserva.

### 2. El MCP de Codex perdía contexto de autenticación

Codex reenviaba ID y dirección, pero omitía directorio durable y las variables
de autenticación. La regresión de configuración reprodujo la omisión.
`CAO_MCP_ENV_NAMES` centraliza nombres de contexto. Claude y OpenCode incorporan
los valores a su configuración privada del MCP propio, preservando overrides.
No se agregan a MCP externos. Codex hereda nombres, sin copiar valores al argv.

Una regresión adicional encontró que un bearer explícito en `env` del perfil
se convertía en un argumento de Codex. Ese override se conserva mediante un
archivo privado `0600`, cargado como variable de entorno al lanzar y eliminado
por `cleanup()`. También se cubre `AUTH0_AUDIENCE`. Una última reproducción
detectó que la primera sesión tmux descartaba `AUTH0_DOMAIN` y
`AUTH0_AUDIENCE` del entorno padre: ahora conserva ambas, para que Codex pueda
heredarlas también cuando el despliegue usa exclusivamente configuración Auth0.

Esto no implementa aislamiento de credenciales entre procesos del mismo usuario,
ni implementa renovación automática de un bearer en un MCP ya iniciado.
El cierre posterior acredita renovación del controlador con los agentes vivos;
los MCP existentes conservan su token todavía vigente.

### 3. Faltaban proyectos de solo lectura

El instalador solo exponía `--workspace` RW. Ahora admite
`--workspace-readonly`, guarda `readonly` y `purpose: project` en el manifiesto
y resuelve rutas canónicas. Rechaza modos RO/RW distintos sobre rutas iguales
o solapadas. Los manifiestos antiguos siguen siendo legibles.

Las pruebas de configuración pasan. Dos contenedores privados sucesivos de la
imagen candidata comprobaron escritura RO rechazada con `EROFS`, escritura RW
visible en el host y lectura del archivo tras recrear el contenedor. No se
sustituye esta prueba real por una inspección de argumentos.

### 4. No existía admisión por proyectos registrados

`CAO_REGISTERED_PROJECTS` activa una política optativa con una lista JSON de
rutas absolutas existentes. La admisión resuelve symlinks y rechaza un
directorio fuera del registro. Una configuración inválida falla de forma
explícita. Sin la variable se conserva la validación genérica.

Se verifica en las fronteras de servicio y tmux. La prueba adicional de
HTTP/SQLite reales rechazó el directorio externo y el escape por symlink antes
de crear un servidor tmux. También se comprueba antes de que Git cree un worktree.
El registro controla el directorio inicial; Docker impone RO. No es un sandbox.

### 5. Un hijo separado sobrevivía al borrado de tmux

Una reproducción real creó un hijo con `start_new_session=True`. Borrar el
terminal tmux dejaba el hijo ejecutándose. La limpieza nueva comprueba usuario,
ID de terminal y socket tmux heredado, fija el proceso con pidfd y revalida
identidad antes de enviar señales. Confirma salida dentro de un plazo acotado.

Al cancelar, fija los procesos antiguos antes de reemplazar la shell, para
preservar la nueva ventana. Otra regresión demostró que una cancelación con ID
incorrecto podía reemplazar una ventana ajena; ahora exige identidad de pane
o window. La fixture antigua de recuperación se ajustó para llevar la misma
marca que escribe la creación de ventanas en producción.

Las pruebas reales verifican borrado, cancelación, conservación de la ventana,
rechazo de identidad ajena y supervivencia de un proceso de otro terminal.
La garantía cubre procesos Linux cuyo contexto heredado es observable en procfs. No cubre
un proceso que lo borra deliberadamente; no se afirma aislamiento adversarial.

### 6. El frontend aceptaba respuestas de tarea inválidas

En el proyecto real, POST/PATCH podían devolver HTTP exitoso con un sobre sin
`task`, ID incorrecto o `completed` no booleano, sin error visible adecuado.
Un error HTML mostraba el mensaje interno del parser JSON.

Diez regresiones fallaron antes del arreglo. `leerTarea()` valida el contrato
y muestra un error legible. Una creación fallida conserva el título; un PATCH
fallido devuelve el checkbox a su estado anterior. Se modificaron únicamente
`frontend/app.js` y `tests/test_frontend.js` del demo en esta tanda.

## Aceptación mantenible

El runner existente mantiene copia del proyecto, HOME, SQLite, puerto y socket
propios, perfiles heterogéneos, plazos y dos rondas con recibos actuales. El
preflight se ejecuta antes de reservar recursos; el contexto temporal también
limpia errores durante preparación.

El modo completo añade:

1. JWT local con JWKS propio y rechazo de credenciales ausentes/caducadas/inválidas.
2. Pregunta/respuesta entre los trabajadores con remitentes reales, estados
   delivered y rechazo de duplicados. El runner no suplanta esos mensajes.
3. MCP externo contra un servicio HTTP privado. Primero comprueba el nonce
   devuelto; después detiene únicamente ese servicio y requiere diagnóstico
   `ConnectionError`. La traza del MCP acredita que se llamó realmente la herramienta.
4. Handoff solicitado por el supervisor con resultado verificado.

Sus helpers, la limpieza del servicio real y dos llamadas al servidor FastMCP
como subproceso real por stdio pasan pruebas (disponible y `ConnectionError`). Los cuatro escenarios se ejecutaron posteriormente con los tres proveedores
y pasaron; preparar el runner por sí solo no fue la acreditación.

## Revisión de composición

- **Autoridad y configuración:** CLI/MCP usan el mismo contrato bearer del API;
  los endpoints siguen validando scopes y caducidad. No se extiende vigencia.
- **Persistencia:** no se cambia el esquema SQLite ni la semántica de inbox.
  Los estados pending/delivered/reconcile no se convierten en éxito de tarea.
- **Orden y replay:** se conservan recibos por turno y rechazo de asignaciones
  repetidas. Los escenarios del runner exigen remitentes actuales y entregas únicas.
- **Lifecycle:** pidfd evita reutilización de PID; fallo de limpieza impide declarar
  eliminación confirmada. El reemplazo fija identidad antes de mutar la ventana.
- **Compatibilidad:** montajes antiguos siguen admitidos; la política de proyectos
  es optativa; CAO genérico y Work conservan sus rutas.
- **Dependencias:** se conserva el grafo de propietarios existente. La utilidad
  de procesos es una hoja; no se introduce otro coordinador, broker ni sandbox.
- **Integración externa:** se usa HTTP/MCP real para helpers; falta la aceptación
  desde un agente. Un doble de proveedor no sustituye ese escenario.

## Reanudación tras login — 2026-10-05

El propietario renovó el login de Claude. El primer intento del runner completo
pasó el preflight y arrancó Claude `4e3d4659`, pero ambas asignaciones se
rechazaron con `verified work identity required`. No se crearon trabajadores
ni se repitieron las asignaciones. El runtime privado terminó y se limpió.
Evidencia: `/tmp/cao-spec006-close/native-after-login.log` y archivo privado
`cao-real-audit-20261005-2f6gv6bu`.

La causa estaba en el fixture de aceptación: su JWT firmado tenía issuer,
audience, scopes y vencimiento, pero no `sub`. Las rutas legacy aceptaban los
scopes; la frontera de asignación exige también una identidad validada. Una
regresión contra el JWKS HTTP real reprodujo `InvalidTokenError` por subject
inválido. Se añadió subject opcional al minter de pruebas y una identidad
exclusiva del run a los tokens del runner. El comportamiento de tokens sin
subject y la validación de producción se conservan.

El aviso de memoria legacy es un rechazo previsto de acceso: ese almacenamiento
solo permite operador local y no acepta JWT de coordinación. No se convierte
ese token en operador local ni se desactiva la protección de memoria.

### Hallazgo de API verificado contra ejecución

Los agentes señalaron RecursionError en peticiones y datos persistidos. Se
contrastó la afirmación: Python 3.12.13 acepta 1.500 y 8.000 niveles; las 11
